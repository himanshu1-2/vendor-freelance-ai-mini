# API Specification

## Status and conventions

This document records the current `fastapi-projects` menu API and separately proposes the missing product contracts. Existing route code is under `service/menu.py`, mounted at `/menu` in `main.py`; **no `/api` prefix is currently mounted there**. The frontend client in `qr-menu/src/lib/menuApi.ts` calls `/menu/...` and defaults the base URL to `http://localhost:8000`.

Use JSON. Current request and response fields use snake_case, matching `src/lib/menuApi.ts`. API versioning, pagination conventions, and a common error envelope are **TBD**.

## Authentication

**Product context:** there is a single administrator. Public admin registration is disabled.

**Implemented:** `POST /auth/register` creates vendor accounts; `POST /auth/login`, `GET /auth/me`, and `POST /auth/logout` provide login/session lifecycle. The admin account is bootstrapped locally with `create_admin.py`. Passwords are hashed and sessions are opaque, server-stored tokens in an HttpOnly cookie. Vendor writes/reads require login and are scoped to the owning vendor; admin can access every vendor. Customer menu reads remain public.

**Configuration:** local CORS origins default to `http://localhost:5173` and `http://127.0.0.1:5173`; `FRONTEND_ORIGINS` overrides them as comma-separated origins. `AUTH_COOKIE_SECURE=true` is required behind HTTPS. Password reset, email verification, login throttling, and admin recovery are not implemented.

## Current implemented endpoints

`{base}` is the configured API origin. The selected FastAPI app currently mounts `/menu` directly (e.g. `http://localhost:8000/menu/...`).

| Method and path | Behavior | Access today | Notes |
|---|---|---|---|
| `POST /auth/register` | Register a vendor account and restaurant | Public | Email/password/name; creates the vendor and starts a session. Admin cannot self-register. |
| `POST /auth/login` | Sign in vendor or admin | Public | Sets an HttpOnly session cookie. |
| `GET /auth/me` | Get current account and role | Session | Returns role and vendor details, if applicable. |
| `POST /auth/logout` | Revoke current session | Session | Clears cookie and server session. |
| `POST /menu/items` | Create catalogue item | Admin or owning vendor | Body uses `vendor_id`, `name`, optional `description`, `category`, optional `is_active`. |
| `GET /menu/vendors` | List registered and legacy active vendors | Public | Returns `{slug, name}[]`, including vendors with no items yet. |
| `GET /menu/items/{vendor_id}` | List active catalogue items for vendor | Admin or owning vendor | `MenuItemRead[]`. |
| `GET /menu/items/{vendor_id}/previously-used` | List active catalogue items included in a saved daily menu on any date | Admin or owning vendor | Returns each distinct item once; selection for the target date remains individual. |
| `PATCH /menu/items/{menu_item_id}` | Partial item update | Admin or owning vendor | Supports name, description, category, `is_active`. |
| `GET /menu/daily/{vendor_id}/{date}` | List daily rows | Admin or owning vendor | `date` is currently a string. |
| `POST /menu/daily/{vendor_id}` | Upsert dated selections (legacy) | Admin or owning vendor | Retained for compatibility. |
| `PUT /menu/daily/{vendor_id}/{date}` | Replace that day's selected items | Admin or owning vendor | Empty list clears daily selections; catalogue rows remain intact. |
| `GET /menu/{vendor_id}/today` | Public today's available items | Public | UTC `datetime.utcnow()` determines today; returns catalogue fields plus daily price/availability. No explicit `published` filter. |
| `GET /menu/{menu_id}` | Get catalogue item by integer ID | Admin or owning vendor | Missing item returns 404. |
| `DELETE /menu/{menu_id}` | Hard-delete catalogue item | Admin or owning vendor | Historical retention still needs soft-deactivation policy. |
| `DELETE /menu/daily/{menu_item_id}` | Delete one daily record by row ID | Admin or owning vendor | Removes a daily association, not the catalogue item. |

The daily-delete handler deletes the row, commits, and returns 204. QR-menu frontend uses `GET /menu/{vendorSlug}/today`, authenticated catalogue and previously-used item reads, `POST /menu/items`, and `PUT /menu/daily/{vendorSlug}/{date}`. Read models use snake_case to match the frontend.

### Current request/response examples

Create catalogue item:

```http
POST /menu/items
Content-Type: application/json
```

```json
{
  "vendor_id": "saffron-table",
  "name": "Charred Corn Chaat",
  "description": "Smoky corn with tamarind.",
  "category": "Small Plates",
  "is_active": true
}
```

Response shape (timestamps/ID generated by backend):

```json
{
  "id": 17,
  "vendor_id": "saffron-table",
  "name": "Charred Corn Chaat",
  "description": "Smoky corn with tamarind.",
  "category": "Small Plates",
  "is_active": true,
  "created_at": "2026-11-09T08:00:00Z"
}
```

Save/update daily items:

```http
PUT /menu/daily/saffron-table/2026-11-09
Content-Type: application/json
```

```json
[
  {
    "vendor_id": "saffron-table",
    "date": "2026-11-09",
    "menu_item_id": 17,
    "price": 295,
    "stock_count": 12,
    "available": true
  }
]
```

Daily response properties are `id`, `vendor_id`, `date`, `menu_item_id`, `price`, `stock_count`, `available`, `created_at`, and `updated_at`.

## Proposed product endpoint set

Preserve the current `/menu` route family and adapt its existing shapes. These are proposed contracts; they are not implemented unless marked current above.

| Method and path | Purpose | Access |
|---|---|---|
| `GET /menu/items?vendor_id={slug}&q={text}&category_id={id}&include_inactive=false` | Catalogue search/filter. Current nearest route is `GET /menu/items/{vendor_id}`. | Admin or owning vendor |
| `POST /menu/items` | Create catalogue item. Existing route; validation applies. | Admin or owning vendor |
| `GET /menu/items/{item_id}` | Read catalogue item. Current equivalent is `GET /menu/{menu_id}`; choose one unambiguous canonical path. | Admin or owning vendor |
| `PUT /menu/items/{item_id}` | Replace/update catalogue item. Current implementation is `PATCH /menu/items/{menu_item_id}`. | Admin or owning vendor |
| `DELETE /menu/items/{item_id}` | Compatibility option: soft-deactivate only, or prefer `PATCH` setting `is_active=false`. Never hard-delete history. | Admin or owning vendor |
| `GET /menu/daily/{vendor_id}/{date}` | Fetch date's current selected items. Draft/publication state is not implemented. | Admin or owning vendor |
| `POST /menu/daily/{vendor_id}` | Legacy upsert; current route upserts a list. | Admin or owning vendor |
| `PUT /menu/daily/{vendor_id}/{date}` | Replace the date's selections atomically; empty list clears that day's selections. | Admin or owning vendor |
| `PUT /menu/daily/{menu_id}` | Update draft and remove omitted daily associations atomically. Must not remove catalogue items. | Admin |
| `POST /menu/daily/{menu_id}/publish` | Validate and atomically publish a draft. | Admin |
| `POST /menu/daily/{menu_id}/unpublish` | Remove current public status according to approved fallback policy. | Admin |
| `GET /menu/{vendor_id}/today` | Public latest published menu for restaurant's local date (or latest publication policy). Existing public route lacks publication check. | Public |
| `GET /menu/daily/{vendor_id}/{date}/preview` | Optional admin-only preview; decide if needed. | Admin |
| `GET /menu/{vendor_id}/qr` | Optional QR destination/metadata; QR image generation can remain in frontend. | Admin |

The requested generic `/api/menu-items` and `/api/daily-menus` paths are **not current conventions**. The table maps the requested operations onto existing `/menu` style. Final path and base prefix are **TBD** and should be agreed before backend/frontend implementation.

Daily draft replacement (example shape; exact schema TBD):

```json
{
  "date": "2026-11-09",
  "items": [
    {
      "menu_item_id": 17,
      "price": "295.00",
      "available": true,
      "stock_count": 12,

  ]

```

Proposed public menu response:

```json
{
  "vendor_id": "saffron-table",
  "name": "Saffron Table",
  "date": "2026-11-09",
  "currency": "INR",
  "published_at": "2026-11-09T07:30:00Z",
  "categories": [
    {
      "name": "Small Plates",
```

Name, currency, category grouping, snapshot timing, and publication metadata in this proposed schema require corresponding database work. The example is not a current response.

## HTTP status codes

| Status | Use |
|---|---|
| `200` | Successful read/update/publish with response body |
| `201` | Created resource (current create route's explicit status is not declared; FastAPI default is 200) |
| `204` | Successful delete/deactivation with no body (current delete routes declare 204) |
| `400` | Invalid cross-vendor payload (current daily upsert uses 400) |
| `401` / `403` | Unauthenticated / authenticated-but-unauthorized request |
| `404` | Unknown resource (current item lookups use 404) |
| `409` | Duplicate/conflicting state (current daily constraint handling uses 409) |
| `422` | FastAPI/Pydantic request validation (default behavior) |
| `5xx` | Unexpected server/database failures |

## Error response structure

**Current:** FastAPI `HTTPException` returns a `detail` field; validation errors use FastAPI's standard structure. Example:

```json
{
  "detail": "Menu item not found"
}
```

A generic `ApiResponse` model exists elsewhere in `fastapi-projects/response.py`, but the menu routes do not use it. Proposed common error envelope, request correlation ID, and validation details are **TBD**. Do not claim a uniform response envelope until implemented and tested.

## Contract and integration gaps

- Backend auth, vendor ownership checks, and dated selection save are implemented; publication, independent drafts, categories, display order, and historical name snapshots are not.
- Backend route root is `/menu`, not `/api/menu`; `qr-menu` currently calls `/menu`.
- Frontend exposes a stable vendor menu URL; QR production domain configuration and download/print remain outstanding.
- Daily inclusion selection is separate from availability in the current editor.
- Current backend public route uses UTC "today", not a restaurant timezone, and selects availability, not publication state.
- Existing backend item delete is hard delete; change policy before production use.
- Define response alias strategy, decimal price serialization, error envelope, CORS origins, and API versioning before treating examples as frozen contracts.
